### A15 / 方案边界 — 重启中断

- 步骤：创建一个三阶段各 4 秒的任务 → 任务进入 `RUNNING/GENERATE` 后强制结束 API 进程（`TaskStop`）→ 重启 API → 用同一 Cookie 查询该任务。
- 预期：任务变为 `FAILED` + `EXECUTION_INTERRUPTED`，运行阶段 FAILED、其余 SKIPPED、结果为空；已完成历史不动。
- 实际：

```
中断前 DB：RUNNING / GENERATE / revision=2
重启后 API：status=FAILED currentStage=GENERATE revision=3
error={"code":"EXECUTION_INTERRUPTED","message":"服务重启导致任务中断，请重新提交","failedStage":"GENERATE"}
steps: ASSET_CHECK=SUCCEEDED GENERATE=FAILED FINALIZE=SKIPPED  result=null
readiness=200（收尾完成后才就绪）
```

- 结论：已验证（真实进程重启，不是模拟）。

## 4. 过程中发现并修复的缺陷

| # | 现象 | 根因 | 处理 |
|---|---|---|---|
| 1 | 会话失效后前端持续发请求（一次 401 触发十几条 401） | `expireSession` 每次递增 `epoch`，而 `useTaskFeed` 的加载 effect 依赖 `epoch`，形成「401 → 重建 → 再请求 → 再 401」循环 | `expireSession` 改为幂等；`load()` 在身份非 `ready` 时直接返回。新增 `useTaskFeed.test.tsx` 断言 401 后只请求一次 |
| 2 | 集成测试随机失败：`StartupRecoveryIT` 预置的 QUEUED 任务被调度器提前领取；B05 时间断言不稳定 | Spring 测试上下文缓存导致多个调度线程同时轮询同一 `pixelflow_it` 库 | 调度闸门默认关闭（`WorkerControl` 初始 paused），启动收尾后按 `pixelflow.worker.auto-start` 开启；测试里 `@BeforeEach` 关闭、需要时显式 resume |
| 3 | `FileFailureIT` 期望 FINALIZE 失败却得到 SUCCEEDED | 空目录作为目标时 Windows 允许 rename 覆盖空目录 | 用非空目录占用目标路径（测试只删除自己创建的两个路径），并让 `writeAtomically` 失败时清理本次临时文件 |
| 4 | `docker compose config` 报 `services.web.healthcheck.test.1 must be a string` | healthcheck 里的 `r.ok ? 0 : 1` 含「冒号+空格」，被 YAML 解析成映射 | 改为单引号标量，复验通过 |
